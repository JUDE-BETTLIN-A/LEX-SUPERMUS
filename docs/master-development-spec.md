# PART 1 – PROJECT UNDERSTANDING

## 1.1 Product Overview

LEX SUPERMUS is a professional networking and opportunity platform for the Indian legal ecosystem.

The platform is inspired by LinkedIn, but focuses exclusively on law students, advocates and legal professionals.

The platform should connect:

1. Law students looking for internships, jobs, mentorship and professional networking.
2. Advocates looking to build their professional identity, connect with students and discover opportunities.
3. Law firms and recruiters looking to identify qualified candidates.
4. Platform administrators responsible for verifying users and maintaining platform authenticity.

## 1.2 Primary User Categories

Create three independent user roles.

| Role | Description |
|---|---|
| STUDENT | Currently enrolled law students |
| ADVOCATE | Enrolled advocates |
| ADMIN | Platform verification and management team |

Keep authentication common, but implement separate registration forms, profile models and verification workflows for students and advocates.

Do not treat a law graduate, enrolled advocate and practicing advocate as identical categories.

# PART 4 – STUDENT REGISTRATION

## 4.1 Student Registration Form

Create a multi-step registration form.

### STEP 1 – Personal Information

Required fields: Full Name, Email Address, Mobile Number, Password, Confirm Password.
Optional fields: Profile Photo, Date of Birth (only if needed for a documented purpose).

Validation: email format, mobile number, password security, duplicate email/mobile check, never store plain-text passwords.

### STEP 2 – Academic Information

Required fields: College / University Name, Course Type, Current Academic Year, Current Semester, Admission / Register Number, Admission Year, Expected Graduation Year, State, District.

Course options: 3-Year LL.B, 5-Year B.A. LL.B, 5-Year B.B.A. LL.B, 5-Year B.Com. LL.B, LL.M, Other recognized law programme.

Allow users to select their institution from a database. If the institution is unavailable, provide an "Other / Request Institution Addition" option.

### STEP 3 – Academic Verification

Allow upload of: College ID Card, Bonafide Certificate, Latest Semester Marksheet, Academic Certificate (when applicable). Do not make every document mandatory. Recommended minimum initial proof: College ID or bonafide certificate. Provide a future DigiLocker integration option.

### STEP 4 – Profile Information (optional)

Areas of Legal Interest, Skills, Languages, LinkedIn Profile, Portfolio, Achievements, Moot Court Participation, Research Publications.

### STEP 5 – Consent and Submission

Display a clear privacy notice. Obtain consent for: processing registration information, reviewing academic documents, conducting the selected verification, displaying approved profile information. Record consent version, timestamp and purpose. Submit registration.

## 4.2 Student Verification Workflow

STUDENT SIGNUP → EMAIL VERIFICATION → MOBILE VERIFICATION → ACADEMIC DETAILS → DOCUMENT UPLOAD → VERIFICATION REQUEST → ADMIN REVIEW / APPROVED DIGITAL RECORD CHECK → VERIFICATION RESULT → STUDENT PROFILE ACTIVATION

Student verification statuses: NOT_STARTED, PENDING, UNDER_REVIEW, VERIFIED, REJECTED, NEEDS_MORE_INFORMATION, EXPIRED.

A student should be able to access their account while verification is pending, but must not receive a verified badge. If verification fails, provide a rejection reason and resubmission option.

## 5.1 Advocate Registration Form

### STEP 1 – Personal Information
Required: Full Legal Name, Email Address, Mobile Number, Password, Confirm Password. Optional: Profile Photo, Date of Birth (if needed for verification).

### STEP 2 – Professional Information
Required: State Bar Council, Advocate Enrollment Number, Enrollment Date, Place of Practice, State, District, City. Optional: Court of Practice, Years of Experience, Areas of Specialization, Languages, Professional Biography, LinkedIn Profile, Law Firm Name.

### STEP 3 – Professional Qualification
AIBE completed? / Certificate of Practice? / Currently practicing? (Yes / No / Not Applicable / Requires review). Do not infer legal eligibility from these answers.

### STEP 4 – Document Upload
Required initial: State Bar Council Enrollment Certificate. Additional where applicable: Advocate Identity Card, AIBE Pass Certificate, Certificate of Practice, other official supporting documents. Do not assume an uploaded image establishes current enrollment or practice status.

### STEP 5 – Consent
Explicit consent for professional credential verification, document processing, relevant official record checks, displaying verified professional details.

### STEP 6 – Submission
Create the advocate profile with verification status PENDING.

# PART 6 – ADVOCATE VERIFICATION ENGINE

## 6.1 Legal Verification Principles
Framework: Advocates Act, 1961; Section 17 (State Bar Council rolls); Section 22 (Certificate of Enrolment); Bar Council of India Certificate and Place of Practice (Verification) Rules, 2015; applicable AIBE and COP requirements.

Do not treat Enrollment Certificate, Enrollment Number, AIBE qualification, Certificate of Practice and current practice status as interchangeable. Do not independently declare someone legally authorized to practice based only on an uploaded certificate.

## 6.2 State Bar Council Selection
State Bar Council master table (Bar Council of Tamil Nadu and Puducherry, Karnataka, Kerala, Andhra Pradesh, Telangana, Maharashtra and Goa, Delhi, Other). Maintain council name, state, official website, contact, verification method, verification URL, integration availability, last reviewed date. Do not invent official APIs.

## 6.3 Enrollment Verification
Collect name, enrollment number, state bar council, enrollment date. Validate format, identify council, check authorized official lookup, compare records, save verification source and result. Missing search result ≠ invalid advocate. No automated lookup → manual verification queue.

## 6.4 Document Verification
Check readability, name matching, enrollment number matching, council matching, date consistency, document type, duplicates, expired/superseded documents. OCR assists but is never authoritative.

## 6.5 Verification Status
NOT_STARTED, PENDING, UNDER_REVIEW, VERIFIED, REJECTED, NEEDS_MORE_INFORMATION, NEEDS_OFFICIAL_CONFIRMATION, EXPIRED, SUSPENDED.

Each verification record contains: user ID, type, status, submitted documents, method, source, reviewer ID, reviewer comments, submission date, review date, last updated date. Only authorized administrators may approve/reject/suspend.

## 6.6 Verification Badge
Badges: Verified Law Student, Verified Enrolled Advocate, Practice Status Confirmed (only when independently supported). Badge has a details view explaining what was verified, when, and what it does not establish.

# PART 7 – DIGILOCKER INTEGRATION

Official resources: https://www.digilocker.gov.in/, https://api.apisetu.gov.in/, https://apisetu.gov.in/digilocker

Use DigiLocker to obtain academic documents shared by students with explicit authorization (degree certificates, marksheets, other supported academic records).

Workflow: apply for Requester Partner access → organization verification → authorized API credentials → OAuth integration per current official documentation → consent → request/receive/validate documents → store only necessary verification information → record result.

Create: DigiLockerIntegrationService, DigiLockerAuthService, DigiLockerDocumentService, DigiLockerCallbackController, DigiLockerConfiguration. Environment variables for all secrets. If partner approval or credentials are unavailable: build a clearly labeled MOCK integration, keep production integration disabled, never claim real verification occurred.

# PART 10 – AUTHENTICATION AND SECURITY

## 10.1 Login
Common login form: Email or Mobile Number, Password, Forgot Password, Remember Me (if implemented securely). After authentication: identify role, check account status, load permissions, redirect to relevant dashboard.

## 10.2 Features
Registration, Login, Logout, Email OTP Verification, Mobile OTP Verification, Password Reset, Password Change, Session Management, Account Lockout / Rate Limiting, Refresh Token Handling (if JWT).

## 10.3 Security Requirements
Spring Security; BCrypt or Argon2 hashing; secure session or JWT; never plain-text passwords; backend role-based authorization; validate all requests; prevent IDOR; CORS restrictions; CSRF where applicable; SQL injection/XSS protection; rate limiting for login and OTP; audit logs; never trust frontend role values; never expose verification documents via public URLs.

# PART 12 – BACKEND REST API DESIGN

## 12.1 Authentication
POST /api/auth/register/student · POST /api/auth/register/advocate · POST /api/auth/login · POST /api/auth/logout · POST /api/auth/verify-email · POST /api/auth/verify-mobile · POST /api/auth/resend-otp · POST /api/auth/forgot-password · POST /api/auth/reset-password · GET /api/auth/me

## 12.2 Student APIs
GET/PUT /api/students/profile · POST /api/students/verification/submit · GET /api/students/verification/status · POST /api/students/documents · DELETE /api/students/documents/{documentId}

## 12.3 Advocate APIs
GET/PUT /api/advocates/profile · POST /api/advocates/verification/submit · GET /api/advocates/verification/status · POST /api/advocates/documents · DELETE /api/advocates/documents/{documentId}

## 12.4 Admin APIs
GET /api/admin/dashboard · GET /api/admin/verifications · GET /api/admin/verifications/{id} · POST /api/admin/verifications/{id}/approve|reject|request-information|request-official-confirmation|suspend · GET /api/admin/audit-logs

All admin endpoints enforce backend permissions. Users cannot approve their own verification requests.

# PART 14 – DOCUMENT STORAGE

Secure private file storage: validate file type/size, unique file identifiers, never trust original filenames, reject executables, malware scanning where supported, store outside public web directory, private object storage, short-lived signed URLs, role-based access restrictions, access event recording, retention/deletion policies.
